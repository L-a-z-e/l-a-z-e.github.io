### HashMap의 내부 구조와 Load Factor의 역할

HashMap의 내부 구조를 복습하며, 기존에 불명확하게 인지하고 있던 데이터 저장 및 해시 충돌(Hash Collision) 처리 방식을 정리했다. 이전에는 충돌 발생 시 일정 개수까지는 Linked List를 사용하고, 그 이후에는 버킷 단위로 연결되는 것으로 잘못 이해하고 있었다.

실제 HashMap은 버킷이 바뀌는 것이 아니라, 하나의 버킷 안에서 데이터의 저장 방식(자료구조)이 변경되는 형태다. 해시 함수를 거쳐 동일한 버킷에 데이터가 할당되는 해시 충돌이 발생했을 때, 내부적으로 다음과 같은 기준을 따른다.

*   **충돌 노드 수 6개 이하:** Linked List 형태로 데이터를 저장한다.
*   **충돌 노드 수 8개 이상:** 탐색 성능을 유지하기 위해 내부 구조를 Red-Black Tree(TreeNode)로 변환한다. 이를 통해 탐색 시간 복잡도를 O(N)에서 O(log N)으로 줄인다.
*   **임계값의 갭(Gap):** 기준점을 7이 아닌 6과 8로 분리한 이유는, 노드가 하나 추가되거나 삭제될 때마다 자료구조가 반복적으로 변환되면서 발생하는 변환 비용(진동 현상)을 방지하기 위함이다.

내부 구조와 더불어 배열 크기 확장 기준인 Load Factor의 동작 원리도 확인했다. Load Factor는 버킷 배열이 얼마나 찼을 때 배열의 크기를 늘릴지 결정하는 비율이며, 자바 HashMap의 기본값은 0.75다.

예를 들어 버킷이 16개일 때 그중 75%인 12개가 차는 순간, 배열 크기를 2배인 32개로 늘리고 기존 데이터를 새 배열에 재배치하는 Rehashing 작업이 수행된다.

이 기준값이 0.75로 설정된 이유는 메모리 사용량과 탐색 속도 사이의 트레이드오프(Trade-off) 때문이다. 이를 표로 비교하면 다음과 같다.

**[표 1: Load Factor 설정값에 따른 트레이드오프 비교]**

| Load Factor | 확장 기준 | 장점 | 단점 |
| :--- | :--- | :--- | :--- |
| **낮음 (예: 0.5)** | 버킷이 50%만 차도 배열 확장 | 충돌이 적어 데이터 탐색 속도가 빠름 | 메모리 낭비가 크고 Rehashing이 자주 발생함 |
| **높음 (예: 1.0)** | 버킷이 100% 찰 때까지 확장 안 함 | 메모리 공간을 매우 효율적으로 사용함 | 충돌이 많아져 Linked List/Tree 탐색 시간이 늘어남 |
| **0.75 (기본값)** | 버킷이 75% 찼을 때 배열 확장 | 시간(탐색)과 공간(메모리) 비용의 최적점 | - |

이와 같이 단일 스레드 환경에서의 HashMap 내부 동작 원리와 메모리-탐색 속도 간의 최적화 기준을 명확히 확인했다. 하지만 실제 애플리케이션은 대부분 멀티스레드 환경에서 동작하며, HashMap은 Thread-safe하지 않다.

### 멀티스레드 환경에서의 ConcurrentHashMap과 원자적 연산

단일 스레드 환경에서의 HashMap 구조를 확인한 후, 멀티스레드 환경에서 Thread-safe한 Map을 구현하기 위한 선택지들을 검토했다. 자바에서 제공하는 주요 대안으로는 `Collections.synchronizedMap`, `Hashtable`, 그리고 `ConcurrentHashMap`이 있다.

먼저 `Collections.synchronizedMap`과 `Hashtable`의 내부 동작 방식을 확인했다. 이 두 가지 방식은 Map 전체를 하나의 모니터(Monitor)로 사용하여 모든 메서드에 `synchronized` 키워드를 적용한다.

```java
// Map 전체에 락이 걸리는 레거시 방식
Map<String, Integer> syncMap = Collections.synchronizedMap(new HashMap<>());
Map<String, Integer> table = new Hashtable<>();
```

이 구조에서는 한 스레드가 데이터를 읽거나 쓰는 동안 Map 전체에 락(Lock)이 걸린다. 다른 모든 스레드는 대기 상태(BLOCKED)로 전환되며, 읽기와 쓰기 작업이 무조건 직렬화된다. 따라서 스레드 수가 증가할수록 병목 현상이 발생하여 애플리케이션의 전체 처리량이 급격히 하락하는 구조적 한계를 가진다.

반면 `ConcurrentHashMap`은 Map 전체가 아닌 버킷(Bucket) 단위로 락을 분할하는 방식을 취하여 동시 처리량을 개선했다. 서로 다른 버킷에 접근하는 스레드들은 락 경쟁을 하지 않으며, 동일한 버킷에 접근할 때만 작업이 직렬화된다.

```java
// ConcurrentHashMap 내부 동작 개념
if (CAS(bucket[i], null, newNode)) {
    // 1. 빈 버킷에 삽입할 때는 락 없이 CAS(Compare-And-Swap) 알고리즘 사용
} else {
    // 2. 이미 노드가 존재하는 버킷에 삽입할 때만 첫 번째 노드에 동기화 적용
    synchronized (firstNode) {
        // 해당 버킷 내에서만 직렬화 처리
    }
}
```

빈 버킷에 데이터를 처음 삽입할 때는 락을 걸지 않고 CAS 알고리즘을 통해 원자적으로 처리한다. 기존 노드가 존재하는 버킷에 삽입이 발생할 때만 해당 버킷의 첫 번째 노드에 락을 건다. 또한 `get()`을 통한 읽기 작업에는 락이 전혀 개입하지 않는다. 노드가 `volatile`로 선언되어 있어 최신 값을 직접 읽으므로, 쓰기 작업과 동시에 일어나더라도 읽기 작업은 블로킹되지 않는다.

하지만 `ConcurrentHashMap`을 사용하더라도 복합 연산 시의 동시성 문제는 여전히 존재한다. 예를 들어 `containsKey`로 데이터 존재 여부를 확인한 후 `put`으로 값을 넣는 방식은 두 연산이 개별적으로 실행되므로 원자성(Atomicity)을 보장하지 못한다. 두 연산 사이에 다른 스레드가 개입하여 값을 덮어쓰는 데이터 유실이 발생할 수 있다.

이 문제를 해결하기 위해 `ConcurrentHashMap`은 '읽기, 판단, 쓰기'의 전체 과정을 단일 트랜잭션처럼 처리하는 원자적 메서드들을 제공한다. 연산 목적에 따라 다음과 같이 메서드를 선택하여 적용할 수 있다.

```java
Map<String, Integer> map = new ConcurrentHashMap<>();

// 1. putIfAbsent: 키가 없을 때만 삽입 (기존 값이 있으면 덮어쓰지 않음)
map.putIfAbsent("user:1", 100);

// 2. computeIfAbsent: 키가 없을 때만 람다식을 실행 (생성 비용이 큰 객체에 유리)
map.computeIfAbsent("user:1", key -> expensiveLoad(key));

// 3. compute: 기존 값을 읽어 변환 로직 적용 후 저장
map.compute("keyword", (key, oldValue) -> oldValue == null ? 1 : oldValue + 1);

// 4. merge: 값이 없으면 초기값, 있으면 기존값과 합산
map.merge("keyword", 1, Integer::sum);

// 5. replace: 특정 상태값과 일치할 때만 교체 (상태 전이 검증)
boolean success = map.replace("order:1", "PENDING", "PAID");
```

각 메서드가 어떤 상황에서 사용되는지, 그리고 기존 방식(get + put 조합)과 비교했을 때 어떤 트레이드오프와 이점을 가지는지 정리하면 다음과 같다.

**[표: ConcurrentHashMap 원자적 메서드 사용 기준 및 비교]**

| 메서드 | 동작 방식 | 주요 실무 활용 패턴 |
| :--- | :--- | :--- |
| **putIfAbsent** | 키가 존재하지 않을 때만 값 삽입 | 단순 초기화 (생성 비용이 적은 데이터) |
| **computeIfAbsent** | 키가 존재하지 않을 때만 람다 실행 후 삽입 | 객체 생성 비용이 클 때 불필요한 생성 방지 |
| **compute** | 기존 값을 읽고 연산한 후 결과를 덮어씀 | 조건부 데이터 변환, 조회수 증가 연산 |
| **merge** | 키가 없으면 초기값, 있으면 기존값과 병합 연산 | 단어 빈도수 카운팅, 수치 누적 합산 |
| **replace** | 현재 값이 예상하는 특정 값과 일치할 때만 변경 | 동시성 환경에서의 주문/결제 상태 전이 처리 |

멀티스레드 환경에서는 `ConcurrentHashMap`이라는 자료구조의 도입 여부뿐만 아니라, 연산의 종류에 따라 적절한 원자적 메서드를 선택해야 한다. 전체 락 방식이 야기하는 성능 저하와 복합 연산이 유발하는 동시성 깨짐 현상의 원리를 이해함으로써, 요구사항에 맞는 안전한 동시성 제어 코드를 작성할 수 있다.
