### 특정 값 탐색과 최댓값 추출: BST와 Heap의 구조적 특성 비교

트리 기반의 자료구조를 학습하는 과정에서 이진 탐색 트리(Binary Search Tree, 이하 BST)와 힙(Heap)의 구조적 차이와 그에 따른 시간복잡도를 분석했다. 두 자료구조 모두 트리 형태를 띠고 있으나, 데이터를 정렬하고 탐색하는 목적과 방식에서 명확한 차이를 보인다.

**노드 간의 대소 관계 원리**

BST의 핵심은 좌우 자식 노드 간의 명확한 대소 관계다. 어느 노드를 기준으로 하든 '왼쪽 자식 노드는 부모보다 작고, 오른쪽 자식 노드는 부모보다 크다'는 규칙이 성립한다. 특정 값을 찾고자 할 때 이 규칙을 통해 탐색 범위를 절반씩 좁혀나갈 수 있으며, 이로 인해 탐색 연산 시 O(log N)의 시간복잡도를 보장한다.

반면 Heap은 좌우 자식 간의 대소 관계를 정의하지 않는다. 오직 부모와 자식 간의 대소 관계만 존재한다.

Max-Heap의 경우 '부모 노드는 자식 노드보다 크거나 같다'는 규칙이 트리의 모든 레벨에 적용된다. 자식 노드들끼리는 어느 쪽이 더 큰지 알 수 없으므로 BST처럼 절반씩 버려가며 특정 값을 탐색하는 것은 불가능하다.

**최대·최솟값 탐색 시의 시간복잡도 검증**

학습 중 Max-Heap에서 최댓값과 최솟값을 모두 O(1)에 찾을 수 있는지에 대한 의문이 있었다. 구조를 다시 분석한 결과, 이는 반만 맞는 사실이었다.

Max-Heap 구조에서는 부모가 자식보다 크거나 같다는 규칙이 항상 유지되므로, 트리의 루트(인덱스 0)에는 구조적으로 전체 데이터 중 최댓값이 위치한다. 따라서 최댓값 탐색은 O(1)에 처리된다. 하지만 최솟값은 구조의 특성상 리프 노드 중 어딘가에 위치한다는 것만 알 수 있을 뿐, 정확한 위치를 특정할 수 없다. 최솟값을 찾으려면 모든 리프 노드를 순회해야 하므로 O(N)의 시간복잡도가 발생한다.

반대로 부모가 자식보다 작거나 같은 Min-Heap에서는 최솟값 탐색이 O(1), 최댓값 탐색이 O(N)이다. 즉, 하나의 Heap 구조만으로는 최댓값과 최솟값 탐색을 동시에 O(1)로 처리할 수 없다.

Java에서 Heap을 활용할 때는 내부적으로 Heap 구조를 사용하는 `PriorityQueue`를 활용한다.

```java
// Min-Heap (Java PriorityQueue 기본 구현)
PriorityQueue<Integer> minHeap = new PriorityQueue<>();
minHeap.offer(30);
minHeap.offer(10);
minHeap.offer(20);
minHeap.peek(); // 10 반환 — 최솟값 O(1)
minHeap.poll(); // 10 반환 및 제거, 이후 내부적으로 힙 재정렬 수행 O(log N)

// Max-Heap (역순 정렬 기준 적용)
PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Collections.reverseOrder());
maxHeap.offer(30);
maxHeap.offer(10);
maxHeap.offer(20);
maxHeap.peek(); // 30 반환 — 최댓값 O(1)
```

**BST의 한계와 구조적 퇴화**

BST는 특정 값 탐색에 O(log N)을 보장하지만, 항상 그런 것은 아니다. 데이터의 삽입 순서가 트리의 최종적인 구조를 결정한다는 제약이 존재한다.


데이터가 오름차순이나 내림차순으로 연속해서 삽입될 경우, 트리가 한쪽으로 길게 늘어지는 편향 트리(Skewed Tree) 현상이 발생한다. 이 상태에 도달하면 구조적으로 데이터를 순차 탐색하는 것과 다를 바 없게 되며, 탐색 시간복잡도는 O(log N)에서 O(N)으로 심각하게 저하된다. 이는 트리 구조를 도입하여 얻고자 했던 성능적 이점이 무효화됨을 의미한다.

**BST와 Heap 구조적 특성 요약**

| 자료구조 | 구조적 특징 | 특정 값 탐색 | 최댓값 탐색 | 최솟값 탐색 |
| :--- | :--- | :--- | :--- | :--- |
| **BST** | 좌/우 자식 및 부모 간 대소 관계 유지 | O(log N) * | O(log N) * | O(log N) * |
| **Max-Heap** | 부모/자식 간 대소 관계만 유지 | 불가 (순회 필요) | O(1) | O(N) |
| **Min-Heap** | 부모/자식 간 대소 관계만 유지 | 불가 (순회 필요) | O(N) | O(1) |

*\* BST의 시간복잡도는 트리의 균형이 유지된다는 가정하에 성립하며, 편향 트리가 될 경우 모두 O(N)으로 저하된다.*

### 편향 트리 문제의 해결과 상황별 Map 자료구조 선택 (HashMap vs TreeMap)

BST가 삽입 순서에 따라 편향 트리로 퇴화할 경우 O(N)의 탐색 시간을 가지는 치명적인 구조적 한계를 확인했다. 이 문제를 해결하기 위해 도입된 개념이 Red-Black Tree다.

Red-Black Tree는 데이터의 삽입이나 삭제 시점에 트리의 편향이 감지되면, 자체적인 회전 연산을 통해 트리의 높이 균형을 자동으로 맞춘다. 이로 인해 데이터가 오름차순이나 내림차순으로 연속 삽입되더라도 개발자가 개입할 필요 없이 항상 O(log N)의 탐색 성능이 보장된다. Java에서 제공하는 `TreeMap`, `TreeSet` 자료구조와, `HashMap`에서 해시 충돌이 8개 이상 발생할 때 내부적으로 사용하는 `TreeNode`가 모두 이 Red-Black Tree를 기반으로 구현되어 있다.

이러한 트리 구조에 대한 이해를 바탕으로, 실무 환경에서 Java의 `HashMap`과 `TreeMap` 중 어느 것을 선택해야 하는지 그 기준을 검증했다. 두 자료구조의 가장 명확한 차이는 내부 데이터의 정렬 여부다.

```java
// HashMap: 해시 알고리즘 기반으로 저장되며, 입력 순서나 데이터의 크기 순서를 보장하지 않음
Map<String, Integer> hashMap = new HashMap<>();
hashMap.put("banana", 2);
hashMap.put("apple", 1);
hashMap.put("cherry", 3);
// 순회 결과: cherry, apple, banana (해시값에 따른 배치로 예측 불가)

// TreeMap: Red-Black Tree를 기반으로 키(Key) 기준 자동 정렬 수행
Map<String, Integer> treeMap = new TreeMap<>();
treeMap.put("banana", 2);
treeMap.put("apple", 1);
treeMap.put("cherry", 3);
// 순회 결과: apple, banana, cherry (항상 알파벳 오름차순 보장)
```

데이터의 단순 삽입과 조회 성능만 비교하면 해시를 사용하는 `HashMap`이 O(1)로 우위에 있다. 그러나 내부 데이터가 정렬된 상태를 유지하는 `TreeMap`의 구조적 특성이 필수적인 3가지 구체적인 상황을 확인했다.

첫 번째는 특정 구간의 데이터를 조회하는 '범위 검색'이 필요한 상황이다. 날짜를 키로 가지는 주식 가격 이력 데이터에서 특정 분기의 가격 데이터만 추출해야 할 때, `HashMap`은 전체 데이터를 순회해야 하므로 O(N)의 시간복잡도를 가진다. 반면 `TreeMap`은 `subMap` 메서드를 통해 트리의 구조적 이점을 활용하여 O(log N)만에 해당 범위의 데이터를 반환할 수 있다.

```java
TreeMap<LocalDate, Integer> priceHistory = new TreeMap<>();
priceHistory.put(LocalDate.of(2024, 1, 1), 50000);
priceHistory.put(LocalDate.of(2024, 3, 15), 55000);
priceHistory.put(LocalDate.of(2024, 6, 30), 48000);
priceHistory.put(LocalDate.of(2024, 12, 31), 62000);

// O(log N)의 시간복잡도로 2024년 2분기(4월 1일 ~ 7월 1일 이전) 구간만 추출
SortedMap<LocalDate, Integer> q2 = priceHistory.subMap(
    LocalDate.of(2024, 4, 1),
    LocalDate.of(2024, 7, 1)
);
```

두 번째는 정확히 일치하는 키가 존재하지 않을 때 기준점과 '가장 가까운 값'을 찾아야 하는 상황이다. 이동 거리에 따른 배달 요금을 산정할 때, 고객의 거리가 4.2km라면 요금표에 4.2km라는 정확한 키가 없더라도 조건을 충족하는 근사치를 찾아야 한다. `TreeMap`은 `ceilingEntry`(크거나 같은 최솟값)와 `floorEntry`(작거나 같은 최댓값) 메서드를 제공하여 이를 즉시 처리할 수 있다. `HashMap`은 키 간의 관계를 알 수 없으므로 이러한 연산이 불가능하다.

```java
TreeMap<Integer, Integer> fareTable = new TreeMap<>();
fareTable.put(1, 3000);   // 1km 이하
fareTable.put(3, 4000);   // 3km 이하
fareTable.put(5, 5500);   // 5km 이하
fareTable.put(10, 7000);  // 10km 이하

// 고객 거리가 4.2km일 때, 4보다 크거나 같은 최솟값 키 탐색
Map.Entry<Integer, Integer> entry = fareTable.ceilingEntry(4); // 키 5 반환, 요금 5500원 적용
```

세 번째는 전체 데이터 중 '상위 또는 하위 N개'를 추출하는 상황이다. 실시간 점수 랭킹 시스템에서 최상위 2명의 데이터를 가져와야 할 때, `TreeMap` 생성 시점에 내림차순 정렬 조건을 부여하면 내부 데이터가 이미 정렬된 상태를 유지하므로, 순회 시 즉각적으로 최상위 데이터를 얻을 수 있다.

```java
// 키(점수) 기준 내림차순 정렬을 적용하여 생성
TreeMap<Integer, String> ranking = new TreeMap<>(Collections.reverseOrder());
ranking.put(9500, "Alice");
ranking.put(8700, "Bob");
ranking.put(9200, "Charlie");
ranking.put(7800, "Dave");

// 이미 점수 역순으로 정렬되어 있으므로 limit(2)를 통해 상위 2명 즉시 추출
ranking.entrySet().stream()
    .limit(2)
    .forEach(e -> System.out.println(e.getValue() + ": " + e.getKey()));
```

두 Map 자료구조의 연산별 시간복잡도를 비교하면 다음과 같은 트레이드오프(Trade-off)가 성립한다.

| 연산 유형 | HashMap | TreeMap |
| :--- | :--- | :--- |
| **단일 요소 삽입/조회 (get / put)** | O(1) | O(log N) |
| **특정 구간 범위 검색** | O(N) | O(log N) |
| **정렬된 상태로 순회** | O(N log N) (별도 정렬 작업 필요) | O(N) (정렬된 상태로 즉시 순회) |
| **최대/최솟값 탐색** | O(N) | O(log N) |

결론적으로, 단순히 키와 값을 매핑하여 저장하고 조회하는 것이 유일한 목적이라면 접근 성능이 뛰어난 `HashMap`을 사용하는 것이 기술적으로 타당하다. 하지만 요구사항 내에 정렬된 순서 보장, 특정 범위의 데이터 검색, 기준과 가장 가까운 근사치 탐색, 최댓값 및 최솟값 추출이라는 4가지 조건 중 하나라도 포함되어 있다면, 이를 O(log N)의 성능으로 안정적으로 처리할 수 있는 `TreeMap`을 선택해야 한다.
